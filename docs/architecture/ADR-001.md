# ADR-001: Generic Registry Core

## Purpose

Record how foundation resources are published and retrieved without coupling the
foundation to feature runtimes.

## Decision

The repository uses a generic registry abstraction with stable resource/version
keys, ownership and compatibility metadata, deterministic records, and sealed
content digests. Both memory and file stores implement a structural store
protocol. Publication rejects duplicate records; file persistence uses an atomic
replace and rejects corrupt or unsupported envelopes.

Evidence is exercised by `agent/tests/test_aios_registry_foundation.py` and
implemented under `agent/src/registries/core/`.

## Alternatives

- Feature-specific global dictionaries.
- Database-only persistence.
- Last-write-wins replacement of an existing version.

## Tradeoffs

Append-style immutability makes corrections require a new version and leaves
discovery/bootstrap to callers. It provides deterministic retrieval and clearer
compatibility boundaries.

## Consequences

Registry records are data, not executable plugins. Callers remain responsible
for selecting compatible records and for any runtime activation.

## Scope

Phase 1 generic registry foundation. Existing independent registries elsewhere
in the repository are not migrated or consolidated by this decision.
